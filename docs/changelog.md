# Changelog

All notable changes to bxvtt are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). The release version (the root `package.json` version, which the server reads at startup and the web build reads at build time, and which `GET /api/health` reports) covers the HTTP `/api` and WebSocket `/ws` protocol in `@bxvtt/shared/protocol`, the `@bxvtt/shared/client` TypeScript SDK, server environment variables, and the web client. `SCHEMA_VERSION` (`8` in `apps/server/src/db.ts`) versions the SQLite schema in `.data/bxvtt.db`, which the server migrates forward automatically at startup, whereas `bxapi` (the loopback HTTP rules server) and `osrlib` (its B/X rules engine) version game rules and save documents separately.

## [Unreleased]

## [0.5.0] - 2026-11-27

This release needs a `bxapi` built on `osrlib` 2.10.0, which is `bxapi` `main` from its pull request 63 onward. Update and restart `bxapi` before you start this version. With an older engine, the server refuses every game request, ability roll, and WebSocket snapshot with `503 bxapi_outdated`.

### Added

- **`GET /api/ability-rolls/{roll_id}/adjustment-limits` (`@bxvtt/server`, `@bxvtt/shared/protocol`, `@bxvtt/shared/client`):** Returns `bxapi`'s `AdjustmentLimits` for a roll and a `class_id` (`BxvttClient.getAdjustmentLimits`), which state how far an ability score trade can move each score and why it stops there. The route applies the ownership, newest-roll, and fixed-class checks of `POST /api/characters/check` and shares its rate limit. ([#60](https://github.com/mmacy/bxvtt/issues/60))
- **A `dismissOnOutsideClick` prop on the kit's `Dialog` (`@bxvtt/web`):** Pass `false` to keep a dialog open when someone clicks outside it. The default is `true`.

### Changed

- **`osrlib` 2.10.0 or later (`@bxvtt/server`):** The server's minimum engine version is 2.10.0, because the trade limits come from `bxapi` since that version. An older engine gets `503 bxapi_outdated`, and `GET /api/health` reports it as outdated.
- **The ability trade step disables controls that can't work (`@bxvtt/web`, `@bxvtt/shared/text`):** Each **Lower** and **Raise** button that can't change its score is unavailable and gives the reason on hover and focus, and lowering moves by the step that `bxapi` states. A badge beside **Reset scores** shows **points to spend**, **points short**, or **Trade complete**, and **Continue** waits until the trade is finished. When no trade is possible, the step says why and offers **Continue**. ([#54](https://github.com/mmacy/bxvtt/issues/54), [#60](https://github.com/mmacy/bxvtt/issues/60))
- **A saved trade that the limits can't produce is dropped (`@bxvtt/web`):** A character that you started in an earlier version and left on a trade that the step can't make now opens with no trade, and you trade again.
- **The wizard names the character last (`@bxvtt/web`):** Step 4 is **Alignment and languages**. You enter the name in the review step's sheet header, where **Suggest a name** moved with it. If the name is empty or can't be used, **Create character** shows the reason under the field and moves focus there. ([#57](https://github.com/mmacy/bxvtt/issues/57))
- **Create character closes the wizard (`@bxvtt/web`):** The wizard stores the character, closes, and returns you to the lobby with the character in the party. The "is ready" view, **Create another**, and **Done** are gone. ([#61](https://github.com/mmacy/bxvtt/issues/61))
- **An unfinished character stays visible in the lobby (`@bxvtt/web`):** The lobby button reads **Resume character** while you have an unfinished character at the table. A click outside the wizard no longer closes it, but **Close** and `Escape` still do. To discard an unfinished character, open the wizard and select **Start over**, which shows while the table lets you roll new ability scores. ([#55](https://github.com/mmacy/bxvtt/issues/55))
- **Maximum hit points on the review step (`@bxvtt/web`):** With maximum hit points on, the review step says your table gives the maximum on the hit die and doesn't describe a roll. ([#56](https://github.com/mmacy/bxvtt/issues/56))
- **Shorter wizard text (`@bxvtt/web`):** The steps drop sentences that repeat a control or explain a rule you didn't break.
- **Class names in labels (`@bxvtt/web`, `@bxvtt/shared/text`):** A class name that stands alone as a label, a card line, or a list entry is capitalized as the SRD writes it, such as "Level 1 Fighter" on a character card and "Magic-User spell, level 1" in the compendium. A class name inside a sentence stays lowercase, as in "A fighter has no special abilities." ([#59](https://github.com/mmacy/bxvtt/issues/59))

### Fixed

- **Phone widths (`@bxvtt/web`):** The wizard and the lobby fit screens 390 px and 320 px wide. The stepper scrolls inside its own box and shows the current step's name only where the whole name fits, the review sheet stacks its columns and wraps its ability cards, and the footer wraps. The outfit step puts the cart under the equipment at 1100 px and narrower, with a badge beside the **Equipment** heading that shows the gold you have left. At phone width it lists equipment as stacked rows (name and **Add**, description, then price and weight) in place of the table. A long character name no longer widens the lobby's cards.
- **Wizard text and behavior (`@bxvtt/web`):** An elf's languages read "An elf speaks", the soldier kit's spare dagger no longer raises a warning on the review step, and a name that the server refuses shows under the name field and takes focus. A saved character that reopens on the review step without a name puts focus in the name field.
- **Closing the wizard while it creates a character (`@bxvtt/web`):** The character still joins the party. When the character is stored, it no longer closes a wizard that you opened in the meantime, and the lobby button returns to **Create a character**.

## [0.4.0] - 2026-11-26

This release needs a `bxapi` built on `osrlib` 2.9.0, which is `bxapi` `main` from its pull request 60 onward. Update and restart `bxapi` before you start this version. With an older engine, the server serves no game and rolls no ability scores: it refuses every game request, every ability roll, and every WebSocket snapshot with `503 bxapi_outdated`, and `GET /api/health` reports `degraded` with the versions for a signed-in user. Without the check, an older `bxapi` couldn't roll with a table's `ruleset`, couldn't report a sub-par roll, and would leave the player view without the spell and valuable fields that the client reads now.

### Added

- **A ruleset for each table (`@bxvtt/server`, `@bxvtt/shared/protocol`, `@bxvtt/shared/client`, `@bxvtt/web`):** A table stores one `osrlib` `Ruleset`, and a referee controls it from the table's settings. The referee starts from **Standard B/X** (`osrlib`'s defaults, which follow the SRD) or **Creation house rules** (`osrlib`'s `creation_house_rules` example, which turns on 4d6 drop lowest and maximum hit points at first level), then changes each rule on its own. The rules cover the SRD's optional rules (a hit die reroll of 1 or 2, and sub-par characters), house rules (4d6 drop lowest, maximum hit points at first level, and the number of ability score rerolls), and the rules for play that the lobby's **Optional rules** panel used to hold. The server rolls ability scores, creates characters, and starts games with the table's ruleset, and every member can read it. ([#45](https://github.com/mmacy/bxvtt/issues/45))
  - **`TableSettings`:** Three new members. `ruleset` is the table's whole `Ruleset`. `ability_score_rerolls` is how many times a player may roll new ability scores after the first roll, from 0 to 99, or `null` for no limit, and defaults to 0. `sub_par_restart` is whether a player may discard a sub-par roll and roll again without using a reroll, and defaults to `false`. `PATCH /api/tables/{t}` accepts all three in `settings`, from a referee only. In the request, `ruleset` holds only the rules to change, the server merges them into the stored ruleset, and a key that isn't a `Ruleset` field or a value that the field doesn't allow gets `422 validation_error`.
  - **`GET /api/rulesets`:** Returns `StartingRulesetList`, the two starting rulesets `standard` and `creation_house_rules` as whole `Ruleset` objects (`BxvttClient.listRulesets`). Both have `hp_reroll_at_first_level` on. A client finds the starting ruleset that a table matches by comparing every `Ruleset` field.
  - **`POST /api/tables/{t}/ability-rolls`:** Any table member can roll, in the lobby or during a game (`BxvttClient.rollAbilities(tableId, body?)`). The response is `bxapi`'s roll with `table_id`, `rules` (a new `CreationRules` object with `ability_score_method`, `hp_reroll_at_first_level`, `max_hp_at_first_level`, `ability_score_rerolls`, and `sub_par_restart`), and `rerolls_left` (`null` without a limit). The server records the table's rules on the roll, and uses that record for the roll's hit points, gold, checks, and creation, so a later change to the table's settings never changes a roll in progress. `GET /api/ability-rolls/{roll_id}` returns the same members.
  - **`GET /api/tables/{t}/ability-rolls/current`:** Returns the user's newest open roll at the table, or `null` when there is none (`BxvttClient.getCurrentAbilityRoll`). A wizard whose draft is gone uses it to continue the roll.
  - **The reroll limit:** A player's first roll is free, and each later roll is a reroll. An open roll is one that made no character and that nothing closed. Unless the table has no limit, the server refuses a roll with `409 ability_rerolls_used` when the player already has `1 + ability_score_rerolls` open rolls at the table. Only the newest open roll can roll hit points or gold, be checked, or make a character, and an older open roll gets `409 ability_roll_superseded`. Both problems include the `roll_id` of the newest open roll, and `ability_rerolls_used` includes `ability_score_rerolls`. Creating a character closes the player's other open rolls at the table. With `sub_par_restart` on, a new roll closes the player's newest roll when `bxapi` reports its scores as sub-par (`rolls.sub_par`), and the closed roll doesn't count against the limit.
  - **`RosterEntry`:** Two new members. `creation_rules` is the `CreationRules` the character was built under, or `null` for a character created before the server recorded them. `rolled_at_other_table` is true when the character's ability scores were rolled at another table, and false when they were rolled here or when the server can't tell.
  - **Existing tables:** Migration 8 gives every existing table the **Standard B/X** ruleset with the hit die reroll turned on, no ability score rerolls, and no sub-par restart. The hit die reroll is therefore on for every new character at those tables, where it used to be a checkbox that each player chose.
- **Table rules in the lobby and on the play screen (`@bxvtt/web`):** The lobby has a collapsible **Rules** panel, and the play screen's **Table settings** dialog has a **Rules** tab beside **Table**. Both hold **Starting rules**, **Optional rules**, **House rules**, and **Rules for play**. A player sees the same settings with every control unavailable. Choosing a starting ruleset sets every switch to match it, and asks first when the table's rules match neither starting ruleset and show as **Custom**. **Ability score rerolls** takes a number or **Unlimited**. A change made during a game applies to the next new game. The **Back-stab from hiding** switch is new, because the table now stores the whole ruleset and every `Ruleset` switch is editable.
- **Roster marks for the referee (`@bxvtt/web`):** A referee sees one badge on a roster card when the character wasn't rolled at this table under the table's current creation rules. **Different rules** lists each rule that differs, **Other table** says the ability scores were rolled elsewhere, and **Rules unknown** marks a character created before the server recorded its rules. The referee decides whether to keep such a character, because bxvtt never refuses one.
- **4d6 drop lowest, maximum hit points, and sub-par characters in the wizard (`@bxvtt/web`):** With 4d6 drop lowest on, the roll step shows four dice for each score and marks the one that `bxapi` dropped. With the maximum hit points rule on, the hit points step shows **Maximum hit points** and **Take the maximum** where it showed **Roll hit points**. With sub-par characters on, a roll that `bxapi` calls sub-par shows a **Sub-par** badge and a **Start again** button, which rolls new scores without using a reroll.
- **`CharacterPreviewRequest` (`@bxvtt/shared/protocol`):** The body of `POST /api/characters/preview` takes an optional `ruleset`, with only the rules that differ from `osrlib`'s defaults, and an optional `seed`. The preview stores nothing, so it needs no roll.

### Changed

- **Characters come from a table's ability roll (`@bxvtt/server`, `@bxvtt/shared/protocol`, `@bxvtt/shared/client`, `@bxvtt/web`):** `CharacterRequest` requires `ability_roll_id`, and `POST /api/characters/check` takes the same body. The server sends the roll's recorded ruleset to `bxapi` for the hit points, the gold, the checks, and the creation, and ignores any `ruleset`, `seed`, or `hp_reroll_at_first_level` that a client sends there. Each new character stores its roll's `CreationRules`. `ability_roll_used` also covers a roll that a later character or a sub-par restart closed. The wizard opens at a table, keeps one draft for each person and table, and starts over at the roll step when a stored draft holds a roll from before rolls belonged to tables.
- **The wizard shows the rules that apply (`@bxvtt/web`):** The class step has no hit die reroll checkbox, and the hit points step shows **Hit die reroll** as **On** or **Off** from the roll's recorded rules. **Roll again** shows only when the table allows rerolls, with a badge such as **2 left** and a reason when none are left. **Start over** is hidden on the roll step, where **Roll again** does the same job, and on the other steps while the player has no rerolls left, because it would clear a roll that the player can't replace.
- **`hp_reroll_at_first_level` leaves the wizard's requests and responses (`@bxvtt/shared/protocol`):** `StartingRollRequest` and `CharacterRequest` no longer take it, `StartingRollsStatus` and `StartingRolls` replace it with `rules` (a `CreationRules`), and the `ability_roll_locked` problem includes only `class_id`. Rolling hit points fixes the class for the roll, but no longer fixes a reroll option, because the roll's recorded rules decide it.
- **A game plays by the table's ruleset (`@bxvtt/server`, `@bxvtt/shared/protocol`):** `StartGameRequest` loses `ruleset`, and `POST /api/tables/{t}/game` starts the game with the table's stored ruleset.
- **Clearer rule labels (`@bxvtt/web`):** The rules for play have shorter labels and hints, such as **Hunger and thirst**, **Friendly fire**, **Passage width**, and **Failed trap removal**, and the hints no longer state numbers that `osrlib` owns. The **Start game** panel names the table's rules as **Standard B/X**, **Creation house rules**, or **Custom rules**.
- **`osrlib` 2.9.0 or later (`@bxvtt/server`):** The server's minimum engine version is 2.9.0. The `bxapi_outdated` problem, the startup log, and the health check's message for the host name it, and `Health.bxapi.outdated` is true for an older engine.
- **Spell and valuable facts come from the player view (`@bxvtt/web`, `@bxvtt/server`, `@bxvtt/shared/text`):** The client reads the fields that `osrlib` 2.9.0 added, where it worked these facts out for itself. ([#46](https://github.com/mmacy/bxvtt/issues/46))
  - **Spell preparation:** The town square's **Spells to prepare** banner and the readiness checklist read each member's `needs_sleep_to_prepare` and `can_prepare_now`, where they searched the feed for the last rest and the last preparation. A restored save in a new session now shows the same advice as the session that made it.
  - **Reversed spells:** The composer and the **Spells** tab read `MemberView.reverses_at` (`memorize`, `cast`, or `null`) to decide when a caster chooses a reversed form, where they assumed that a spell in the spell book was chosen when memorizing. A custom class that doesn't follow the built-in pattern now gets the right choice.
  - **Spell modes:** The **How to cast** options read the mode's `display_name` from the spell catalog, such as "Blind a creature", where they cut a label out of the mode's description. A form with one mode shows the spell's name. The sleep spell's modes read "Put a creature with 4+1 Hit Dice to sleep" and "Put creatures of 4 Hit Dice or lower to sleep".
  - **The feed's spell mode:** A cast of a spell with several modes reads "Spell mode: Blind a creature.", where a reversed light spell read "Spell mode: Blind" from the mode's key. A spell with one mode, and a spell that the built-in catalog doesn't have, show no mode line.
  - **Valuable names:** A gem or a piece of jewellery with a name of its own takes it from the view's `valuable_names`, keyed by instance ID, where the client paired each pile's `contents` with its `items`. A valuable rolled on the treasure tables has no entry, and reads by its kind in `item_names`.
- **Database schema (`@bxvtt/server`):** `SCHEMA_VERSION` is 8. Migration 8 adds the table's ruleset, reroll limit, and sub-par setting to `tables`, the table, recorded rules, sub-par flag, character, and closing time to `ability_rolls`, and the creation rules to `characters`. An ability roll from before the migration has no table, so the server treats it as one the player doesn't have and the player rolls again. A character from before the migration has no recorded rules. The server migrates an existing database at startup.

### Removed

- **`POST /api/ability-rolls` (`@bxvtt/server`, `@bxvtt/shared/client`):** Ability rolls belong to a table now. Use `POST /api/tables/{t}/ability-rolls`. `BxvttClient.rollAbilities(body?)` is `rollAbilities(tableId, body?)`.
- **Optional rules panel in the lobby (`@bxvtt/web`):** Its switches are in the table's rules, so one stored ruleset is the only place that sets a rule. Its **Reset to standard rules** button is gone, because choosing **Standard B/X** in **Starting rules** does the same.
- **`StartGameRequest.ruleset` (`@bxvtt/shared/protocol`):** Set the rules on the table before you start the game.

### Fixed

- **A caster with nothing memorized was always told to rest (`@bxvtt/web`):** The reason a caster can't cast said "Rest for a night, then prepare spells" even when the caster could prepare right away. It says to rest only when the caster needs sleep to prepare, and otherwise says to prepare spells from the **Spells** tab. ([#46](https://github.com/mmacy/bxvtt/issues/46))

## [0.3.0] - 2026-11-26

This release needs a `bxapi` built on `osrlib` 2.8, which is `bxapi` `main` from its pull request 58 onward. Update and restart `bxapi` before you start this version. With an older engine, the server serves no game: it refuses every game request and WebSocket snapshot with the new `503 bxapi_outdated` problem code, and `GET /api/health` reports `degraded` with the versions for a signed-in user. Without the check, an older `bxapi` would leave the player view without the item names, emptied caches, room trap states, and caches in reach that the client reads, the battle board unable to check declarations, and `bxapi` accepting a player's out-of-battle spell or item aimed at a creature the party hasn't met. With a `bxapi` older than pull request 51, the character wizard's checks also fail.

### Added

- **Leave and delete a table from the table menu (`@bxvtt/web`):** The lobby header has a new **Table menu**, and the play screen's table menu gains **Delete table** for referees. Every member can **Leave table** from either screen. The leave dialog says when leaving also deletes the table, and it tells the only referee of a table with other members to make another member a referee or delete the table. When a referee deletes a table, the other connected members return to their table list, where a notice names the table and who deleted it.
- **Sign out and delete profile (`@bxvtt/web`, `@bxvtt/server`, `@bxvtt/shared/client`):** The profile menu has **Sign out** and **Delete profile**, backed by `POST /api/users/me/sign-out` and `DELETE /api/users/me` (`BxvttClient.signOut` and `BxvttClient.deleteMe`). Signing out invalidates the token on the server, and the dialog lists the tables the person can come back to through the rejoin flow. Deleting a profile takes the user out of every table as leaving does, deletes their stored characters, and keeps what they wrote in shared tables under "A former member". Other tabs in the same browser follow a sign-out, a deletion, or a new sign-in.
- **Hit point and starting gold rolls in the character wizard (`@bxvtt/web`, `@bxvtt/server`, `@bxvtt/shared/protocol`):** The wizard has a seventh step, **Hit points and gold**, where the player rolls each and sees the dice `bxapi` rolled. Rolling hit points fixes the class and the first-level reroll option for those ability scores, so a roll can't be made again by going back or reloading. New routes `GET /api/ability-rolls/{roll_id}/starting-rolls`, `POST /api/ability-rolls/{roll_id}/hit-points`, and `POST /api/ability-rolls/{roll_id}/gold` read and make the rolls, and new problem codes `ability_roll_locked`, `hit_points_not_rolled`, and `gold_not_rolled` refuse a request that would reveal a roll the player hasn't made.
- **Combat playback controls (`@bxvtt/web`):** The playback strip has pause and resume (`K`), step back (`,`), step forward (`.`), and four speeds, next to skip (`Esc`). The viewer's speed is saved in their preferences. Playback is local to each viewer, so pausing holds up nobody else.
- **Documentation link and version on every screen (`@bxvtt/web`):** Every screen shows a **Docs** link to <https://mmacy.github.io/bxvtt/> and the bxvtt version in its bottom left corner. The version is the root `package.json` version, written into the client at build time.
- **Hover help in the design kit (`apps/web/src/ui`):** `Button`, `IconButton`, `LinkButton`, `ToolRailButton`, `ActionBarMenu`, `TabsTrigger`, and `SegmentedControl` options take a `tooltip`, and an icon-only control shows its label as its tooltip. A control with `disabled` and a `disabledReason` stays focusable, sets `aria-disabled`, and shows the reason on hover and on keyboard focus. Menu items, command palette actions, and list items show the reason under their label. `NumberInput` takes `minReason` and `maxReason`. An ESLint rule rejects the native `title` attribute on an interactive element.
- **`commandModesSentence` (`@bxvtt/shared/text`):** Builds a sentence that says when a command works from the `allowed_modes` in `bxapi`'s command catalog, such as "You can search only while exploring. The party is in town now."
- **`Banner` `announce` prop (`apps/web/src/ui`):** `announce` takes `alert`, `status`, or `none` and sets how a screen reader learns of a banner. A warning or danger `Banner` is still an alert by default. Pass `status` or `none` for a banner that appears each time a view opens, such as the battle composer's note that an action won't work.
- **Hide in battle (`@bxvtt/web`, `@bxvtt/shared/protocol`):** The declaration composer has a **Hide** tab for a character who can hide this round, and a hiding character shows a **Hiding** badge on the battle board. The board never says whether a hide worked, because the referee's roll stays secret, and it says when a hide or a back-stab won't work. `DeclarationBody.action` accepts `hide`, a new `osrlib` 2.7 action, so a client author can declare it with `PUT /api/tables/{t}/game/declarations/{member_id}`.
- **Battle round preview (`@bxvtt/server`, `@bxvtt/web`, `@bxvtt/shared/protocol`):** The board shows why a declaration won't work before anyone resolves the round, and the range track marks where each character will stand after the declared moves. Whenever the server builds the declarations state with at least one stored declaration, it calls `bxapi`'s `POST /v1/sessions/{id}/battle-round/preview`. The new `DeclarationsState.projection` (`RoundProjection | null`) holds `advance_feet` by member and `front_rank` by group. A preview failure leaves `refusals` empty and `projection` `null`, and sets the new `DeclarationsState.preview_unavailable` to `true`, so a client can tell "nothing would be refused" from "the server couldn't check". The board then says "Actions can't be checked right now. If one won't work, you'll find out when the round resolves." and keeps **Resolve round** available.
- **`bxapi_outdated` problem code (`@bxvtt/shared/protocol`, `@bxvtt/server`, `@bxvtt/web`):** The server answers `503 bxapi_outdated` to a game request, and sends a WebSocket `error` with the same code, while `bxapi` runs an `osrlib` older than 2.8.0. `bxapi_unavailable` still means that the server can't reach `bxapi`. The new `Health.bxapi.outdated` flag says the same to anyone, including a reader without a token, because it reveals no version. The home page shows a banner for an out-of-date game service, and a game request shows "The game service is out of date".
- **`save_unreadable` problem code (`@bxvtt/shared/protocol`, `@bxvtt/server`, `@bxvtt/web`):** `POST /api/tables/{t}/saves/{id}/restore` answers `502 save_unreadable`, where it answered `422 content_invalid`, when `bxapi` can't read a save because its rules engine was updated after the save was made. The dialog says to restore a newer save or start a new game.
- **Spells from the game's own catalog (`@bxvtt/server`, `@bxvtt/shared/protocol`, `@bxvtt/shared/client`):** `GET /api/tables/{t}/game/rules/spells/{spell_id}` (`BxvttClient.getSessionSpell`) returns `bxapi`'s `SpellTemplate` from the session's catalog to any member of the table, so a client can show the description, modes, and reversed form of a spell that the adventure bundles. It answers `404 not_found` for a spell that the player view doesn't name in `spell_names`, the same as for a spell that doesn't exist. `SpellId`, `SessionSpellParams`, and `SpellTemplate` are new in `@bxvtt/shared/protocol`.
- **Who can hide or back-stab, in the round projection (`@bxvtt/server`, `@bxvtt/shared/protocol`):** `RoundProjection.can_hide` and `RoundProjection.can_back_stab` list the declarers who could declare a hide or a back-stab beside the other stored declarations, from `bxapi`'s battle round preview. Offer the two actions from these lists when `DeclarationsState.projection` isn't `null`, and from `view.encounter.can_hide` and `view.encounter.can_back_stab` otherwise.
- **Plural item names on feed entries (`@bxvtt/server`, `@bxvtt/shared/protocol`, `@bxvtt/shared/text`):** `EntryNames.items_plural` records what to call two or more of each item that an entry's events name, from the player view's `item_names_plural`, so a line reads "2 vials of holy water". An entry stored before this release has none, and the text forms the plural itself. `TextContext.itemsPlural` and `extendContextWithNames(ctx, names, plurals)` carry the plurals in the text package.
- **Referee notes on adventure features (`adventures/`):** `osrlib` 2.8 adds `FeatureSpec.referee_notes`, text that the adventure's author writes for the referee alone. The player view never contains it, and the server sends it to referees inside the adventure document. The `feature()` helper in `adventures/tools/lib.mjs` passes it through, and thirteen caches in the two sample adventures use it for what a container holds, whose money it is, and how a trap is hidden. See [Author and validate adventures](adventures/authoring-and-checking.md#design-tips-for-multiplayer-fog-of-war).
- **Spells tab built from the player view (`@bxvtt/web`):** The character sheet's **Spells** tab reads each member's slots, the spells they can prepare, and the spells they can learn from the player view (`spell_slots`, `preparable_spells`, `learnable_spells`, and `spell_levels`), and no longer reads a class's progression table. An adventure's bundled spells appear in the tab and the dialogs like built-in ones, with their details from `GET /api/tables/{t}/game/rules/spells/{spell_id}`, and a custom caster class shows its own slots. A **Slots** row shows each level's slots as "1st level 1 of 2". The prepare dialog groups spells by level with a count of the slots chosen, such as **1 of 2**, and lists a reversed form as its own row with a **Reversed** badge. The learn dialog is titled **Learn a spell**, names each spell's level only when its list spans levels, and confirms with **Learn** followed by the spell's name, where it read "Teach" and **Add to spell book**. ## [0.1.0] - 2026-11-22

### Added

- **Multiplayer server and SQLite store (`@bxvtt/server`):** Fastify serves 66 HTTP endpoints under `/api` and real-time state updates over `/ws`, calling `bxapi` over loopback HTTP for all rules execution. The server stores users, tables, 100-bit Crockford Base32 invite codes, member roles (`referee` and `player`), lobby rosters, character seats (linking party members to players), caller assignments (designating who speaks for the party), feed entries, notes, map annotations, monster target handles, pending battle declarations, and `bxapi` cleanup queues in SQLite (`node:sqlite`, schema version 5). State-changing game requests enforce `expected_revision` optimistic concurrency (`409 revision_conflict`) and `Idempotency-Key` replay safety, errors return RFC 9457 `application/problem+json` documents with stable `code` strings, and the server reports full `bxapi` client quotas via `507 bxapi_storage_full` while logging warnings past 80% usage. See [Architecture](architecture.md).
- **Role-based projections and command authorization:** Every HTTP response and WebSocket broadcast (`snapshot`, `game`, `feed`, `annotations`, `notes`, and `rejoin_requests`) filters state per recipient on the server, omitting `RefereeState`, referee-visibility events, full adventure JSON, referee notes, unmapped-level annotations, and secret rolls from player payloads. The server derives `game.scene` strictly from `osrlib` party knowledge (`explored` cells, entered areas, found, sprung, or removed traps, found tricks, and resolved encounters) and issues persistent 96-bit `tgt_` target handles for visible monsters so players never receive internal `bxapi` monster IDs or unrevealed lair hoards. Before forwarding a command to `bxapi`, the server classifies its JSON command schema into member, party, referee, or battle-resolution permissions and verifies the sender's role and seat. In the browser, referees can toggle the **Referee lens** (`Shift+L`) to render the player projection locally when also playing a character.
- **Browser identity, tunnel sharing, and returning-player rejoin:** Users authenticate with origin-scoped 256-bit `bxt_` bearer tokens stored as SHA-256 digests on the server. Running `npm run share` publishes `127.0.0.1` over a public HTTPS Cloudflare quick tunnel (`cloudflared`) with an automatic 144-bit `BXVTT_HOST_KEY` and `BXVTT_PUBLIC_ORIGINS` allowlist while `bxapi` remains private on loopback. When a tunnel URL or browser changes, `/api/rejoin/*` runs a referee-approved rejoin flow using a 256-bit polling secret, a 30-second claim window, automatic cancellation when the visitor leaves, and 90-day `token_retired` tracking to restore the player's existing identity, characters, and seats. See [Play over the internet](getting-started/share-online.md).
- **Transport, input, and rate-limit hardening:** Token buckets throttle requests per IPv4 address, IPv6 `/64` prefix, and authenticated user alongside per-user and per-table resource quotas. The server enforces 64 KiB JSON body limits (8 MiB for adventure uploads), rejects prototype-pollution keys and deep JSON nesting (past depth 64), rejects ASCII/Unicode control characters and bidirectional overrides in display strings, caps WebSocket client frames at 16 KiB, requires WebSocket `Origin` matches and authentication within 10 seconds, and sends strict HTTP security headers (`Content-Security-Policy` with `script-src 'self'`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy`, and proxy-aware `Strict-Transport-Security`). See [Security and trust model](hosting/security.md).
- **Protocol schemas, TypeScript SDK, and event prose (`@bxvtt/shared`):** Zod v4 schemas in `@bxvtt/shared/protocol` validate every HTTP request, response, RFC 9457 problem code, and WebSocket message, paired with OpenAPI-generated `bxapi` types in `@bxvtt/shared/bxapi` (`npm run gen:bxapi`). `@bxvtt/shared/client` exports `BxvttClient` and `TableConnection` with typed methods for all 66 endpoints, automatic heartbeats, exponential-backoff WebSocket reconnection, and `feed_after` sequence catch-up, while `@bxvtt/shared/text` formats `osrlib` game events and rule rejections into B/X table prose. See [HTTP API, WebSocket, and SDK](reference/http-and-websocket.md).
- **Character wizard, character sheets, and lobby setup (`@bxvtt/web`):** A six-step wizard guides character creation across all seven B/X classes (cleric, dwarf, elf, fighter, halfling, magic-user, and thief), including 3d6 ability rolls, prime-requisite adjustments, alignment and bonus languages, arcane starting spells, and equipment shops with class kits validated non-destructively via `POST /api/characters/check`. Character sheet drawers display B/X combat stats, encumbrance, conditions, light controls, item transfers and drops, spell memorization, spell-book learning, and out-of-battle spellcasting. The lobby provides marching-order arrangement, seat and caller assignment, invite rotation, and controls for all 13 `osrlib` optional rules.
- **Town services and canvas dungeon map:** Five town tabs cover the outfitter (with multi-character carts and dungeon-readiness reminders), temple services (`cure_light_wounds` through `raise_dead` paid from pooled party gold), gem and jewellery sales, resting (one turn, a night, or a full day), and spell preparation. In dungeons, a custom HTML5 canvas renderer draws explored 10-foot cells under fog of war in three themes (blueprint, torchlit, and parchment) with zoom, pan, and party-follow camera controls, a minimap, contextual door, trap, treasure, and stair actions, a distance ruler, player-colored pings, freehand strokes, numbered note pins, and keyboard cell-cursor navigation with screen-reader announcements.
- **Encounters, simultaneous battle rounds, and combat playback:** Encounter controls support parley, waiting, evasion (with coin or food distractions), turning undead, item hand-offs, and engaging battle. During battle, `PUT /api/tables/{t}/game/declarations/{member_id}` coordinates simultaneous per-character declarations across seats with live shared status, conservative rank- and equipment-aware quick actions, gaze-defense choices, and automatic or manual `resolve_battle_round` resolution. When `bxapi` refuses a round, the server attributes nameless rejections to the offending character via non-advancing `bxapi` probes without clearing declarations. Accepted rounds play back beat by beat and conclude with aftermath loot cards or victory and game-over summaries.
- **Feed, quest journal, shared notes, and B/X rules compendium:** The chronological table feed combines Markdown chat, multi-recipient and referee whispers, `bxapi`-backed `/roll` slash commands and dice-tray rolls (including secret referee rolls), and narrated game events with unread dividers, category filters, text search, and backward pagination. The three-tab journal tracks active and completed quests, dated chronicle entries, and auto-saving 50,000-character shared party notes with optimistic conflict resolution (`Keep mine`, `Take theirs`, or `See both`). The built-in rules compendium provides faceted search across classes, spells, monsters, equipment, magic items (behind a player spoiler gate), languages, reference tables, actions, and the Open Game License 1.0a notice from gzip-compressed, `ETag`-cached `/api/catalogs/*` bundles.
- **Referee workspace and campaign saves:** An eight-tab referee panel (`Now`, `Act`, `Story`, `Key`, `Roll`, `Log`, `Notes`, and `All`) provides live room keys, peaceful encounter resolution, quest, flag, and trigger controls, post-teleport trigger prompts, stateless `bxapi` generators (treasure types A-V, monsters, room stocking, and NPC parties) with seed replay, full referee event logs, private notes, and schema-driven forms for all 23 `bxapi` referee commands. Tables store up to 100 manual saves plus the 10 newest milestone autosaves, support `.bxsave.json` exports, and restore saved sessions from mid-game, end screens, or the lobby (`Continue from a save`) with automatic seat remapping.
- **Bundled adventures, authoring builder, and automated verifier (`adventures/`):** Every server offers two original `osrlib` modules compiled from `adventures/src/*.mjs` (*The Drowned Bell*, a 3-level, 36-area campaign dungeon, and *The Toll at Crookback Bridge*, a 1-level, 13-area single-session module) alongside `bxapi`'s built-in *The Barrow of the Forgotten King*, plus per-table custom `.json` upload validation (up to 8 MiB) and live `adventures/` directory scanning. Zero-dependency scripts in `adventures/tools/` provide an ASCII grid compiler (`LevelBuilder` in `build.mjs`) and an automated static and live `bxapi` verifier (`check.mjs`) that checks schema validity, entrance reachability, level transitions, keyed encounters, triggers, and quests. See [Included and custom adventures](adventures/included-adventures.md) and [Author and validate adventures](adventures/authoring-and-checking.md).
- **Design system, verification suites, and documentation site:** `@bxvtt/web` builds on a token-driven UI kit (`apps/web/src/ui`, with component galleries at `/kit` and `/kit/table`) using Radix UI primitives, self-hosted Fraunces, Atkinson Hyperlegible Next, and Rokkitt variable fonts, custom B/X class, equipment, and die SVGs, full keyboard navigation, code-split client bundles, and in-memory Brotli and gzip asset serving. Automated checks cover TypeScript, ESLint, Prettier, Vitest unit and live-`bxapi` server integration suites (including scans ensuring player responses never include referee data), multi-browser Playwright end-to-end game and `axe-core` accessibility suites (`e2e/`), GitHub Actions CI against production bundles, and a Docusaurus 3.10 documentation site (`website/` and `docs/`) with light and dark torch-ember themes.
